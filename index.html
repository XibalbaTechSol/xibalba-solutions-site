The Gap

What most agent deployments get wrong.

Three failure modes show up as soon as an agent leaves a demo and touches real systems.

🧠

Context resets every session

An agent's memory usually dies with its process. Nothing carries forward — no evidence of what it learned, no record of why it acted the way it did.

🛡️

Nothing stops a compromised agent

Most deployments trust the agent to behave. When one doesn't, there's often no local enforcement layer between it and the device it's running on.

⚖️

Claims aren't independently verifiable

An agent's own account of its behavior isn't evidence. Without an independent record, a counterparty has to take its word for it.

Agent Memory 01

Xibalba Cortex

“Most agent memory systems store embeddings, not evidence.”

A provenance-aware graph memory MCP server. Every fact is linked to its source, every extraction is a reviewable proposal — never auto-written — and every retrieval trace is independently verifiable, not just trusted.

  • Evidence-linked memory: every fact carries its source and hash.
  • Hybrid retrieval: lexical, vector, graph, and temporal signals are fused and persisted.
  • Human-controlled writes: extraction becomes a proposal, never an automatic write.

Status: design-partner stage — the store schema and MCP contract are frozen for v1, but this is a clone-and-run project (no PyPI package yet).

Endpoint Security 02

Xibalba Shield

“Shield fights fire with fire: local agent-runtime guardrails, kernel-level telemetry, and deterministic policy to constrain the agents operating on the device.”

Traditional endpoint tools understand processes, files, and network flows. AI agents operate a layer above that — they retrieve context, choose models, and invoke tools with semantic intent. Shield governs both layers.

  • Agent-aware guardrails: six hooks from ingress to post-action verification.
  • Local telemetry: Linux eBPF sensors watch process, file, and network activity.
  • Fail-closed containment: OPA/Rego policy plus SIGSTOP/SIGCONT and cgroup isolation.

Status: pre-alpha on our own L0–L3 readiness scale — Linux-first, design-partner/pilot stage, not yet production-hardened.

Xibalba Cortex

Memory with a chain of custody.

Cortex is a provenance-aware graph memory MCP server for teams that need to know not only what an agent remembers, but where the memory came from and how it was retrieved.

For teams that need

Reviewable context, reproducible retrieval, and a memory layer that can be audited after the fact.

Integration surface

Run locally or host the authenticated MCP server over stdio or streamable HTTP.

flowchart LR
  A[Agent] --> M[MCP server]

  L & V & G & T --> F[RRF fusion]

Boundary: extraction proposes; it never silently writes. Current stage: design-partner, clone-and-run.

Xibalba Shield

Security at the point of action.

Shield gives AI agents local guardrails and endpoint visibility, so policy decisions do not depend on a cloud round-trip or an agent describing its own behavior accurately.

For teams that need

Deterministic policy, Linux endpoint telemetry, and containment when an agent crosses a boundary.

Integration surface

Six runtime hooks, OPA/Rego policy, eBPF sensors, and resumable process or cgroup controls.

flowchart LR
  A[Agent action] --> H[Guardrail hooks]
  H --> P[OPA / Rego]
  P -->|allow| X[Execute]
  P -->|deny| D[Block + receipt]
  P -->|contain| K[Freeze / isolate]
  S[eBPF sensors] --> O[Observable event]
  O --> Q[Evidence export]
  Q -. optional .-> I[Integrity Core]

Boundary: local enforcement is standalone; evidence export is additive. Current stage: pre-alpha pilot.

Cortex and Shield remain useful on their own. Integrity Core is the protocol layer for cases where a third party needs to verify who an agent is, how it has behaved, and whether a risky action should be allowed.

Reputation, Precisely Defined

How the AIS score is actually computed.

AIS (Agent Integrity Score) is not a single number pulled from a black box — it's a weighted geometric mean of four independently-measured signals, each computed from real telemetry. This is the exact formula, taken directly from the scoring engine's implementation.

$$AIS = \left( S_{entropy}^{0.30} \cdot S_{grounding}^{0.30} \cdot S_{sacrifice}^{0.20} \cdot S_{compliance}^{0.20} \right) \times \mathrm{ZK_{boost}}$$

Entropy

weight 0.30

Rewards stability, not raw performance level. Computed from the variance of an agent's reported task performance over a trailing 30-day window — a Gaussian-style decay, so small variance barely moves the score, but unbounded variance saturates toward zero fast.

$S_{entropy} = e^{-1.5 \, v^2} \times 1000$  —  x-axis: performance variance (v), y-axis: score 0–1000

Grounding

weight 0.30

Linear, by design — no curve to game. Measures the Human Grounding Index: the fraction of the agent's actions in the period that were checked against real human-in-the-loop feedback.

$S_{grounding} = \mathrm{clamp}(hgi, 0, 1) \times 1000$  —  x-axis: Human Grounding Index (0–1), y-axis: score 0–1000

Sacrifice

weight 0.20

Logarithmic and deliberately saturating — an anti pay-to-win curve. Measures verified compute-hours committed by the agent; a whale doesn't score proportionally higher for spending more.

$S_{sacrifice} = \min\!\left(\dfrac{\log_{10}(\mathrm{hours}+1)}{3},\ 1\right) \times 1000$  —  x-axis: verified compute hours, y-axis: score 0–1000

Compliance

weight 0.20

Linear inverse. Measures the fraction of the agent's telemetry events flagged by the BCC/OPA policy pipeline during the period — more flags, lower score, directly.

$S_{compliance} = (1 - \mathrm{clamp}(p, 0, 1)) \times 1000$  —  x-axis: policy-flagged event ratio (p), y-axis: score 0–1000

Why a geometric mean, not an average

Because AIS multiplies each component raised to its weight rather than averaging them, a single zero-scoring component drives the entire score to zero — $x^w = 0$ whenever $x = 0$. Perfect entropy, grounding, and compliance with zero verified compute still produces an AIS of exactly 0.0, not a partial-credit average around 800. This is intentional and covered by the scoring engine's own test suite. Reported AIS is additionally capped by verification tier — 300 / 600 / 850 / 1000 for tiers 0 through 3 — so a score can never imply more identity verification than an agent has actually completed. A verified zero-knowledge reputation-boost proof (real Noir/Barretenberg circuit) multiplies the final score by 1.15×.

Questions

Before you reach out.

Is any of this production-ready?

Not yet, and we say so directly on each product page. Cortex is design-partner/clone-and-run stage. Shield is pre-alpha on its own L0–L3 readiness scale. Integrity Core is a testnet prototype with real deployed contracts but single-operator key custody. If you need production guarantees today, talk to us about timeline and scope before committing.

Can we self-host instead of using anything we host for you?

Yes — all three products are open source and designed to run on infrastructure you control. Self-hosting is the default path, not an enterprise add-on.

Do we need Integrity Core to use Cortex or Shield?

No. Both run standalone with zero dependency on Integrity Core. It's only relevant if you need on-chain, third-party-verifiable identity and reputation on top of what Cortex and Shield already give you locally.

What does a design partnership actually involve?

Direct access to the team building this, a say in what ships next, and hands-on help getting your first real deployment running — in exchange for being an early, honest reference case as the products mature.

How do we evaluate the security posture before deploying?

Start with the code — it's public. Then talk to us: we'll walk through the current threat model and known gaps for your specific product(s) of interest before you commit to anything.
